# Стратегический роадмап Data Mesh — «Будущее 2.0»

---

## Ключевые роли

| Роль | Зона ответственности |
|---|---|
| **Data Product Owner** | Отвечает за данные домена как за продукт: качество, SLA, схемы событий, доступность |
| **Data Engineer** | Строит Kafka-топики, Flink-пайплайны, витрины ClickHouse; поддерживает Schema Registry |
| **BI-аналитик** | Работает с Data Products в self-service портале; строит дашборды и отчёты |
| **Platform Engineer / SRE** | Поддерживает Kafka, Kubernetes, облачную инфраструктуру; пишет runbooks |
| **Архитектор (Arch Committee)** | Стандарты событий, ADR, арбитраж cross-domain конфликтов |

---

## Этапы внедрения

### Этап 1 — Пилот (месяцы 1–6)

**Цель:** Доказать жизнеспособность событийной архитектуры на одном домене.

| Активность | Ответственный | Результат |
|---|---|---|
| Развернуть Managed Kafka + Schema Registry | Platform Engineer | Рабочая шина событий |
| Назначить Data Product Owner в Clinic | CTO + менеджер трансформации | Первый владелец данных |
| Реализовать Legacy Adapter (Camel → Kafka) | Integration Team | ESB-события в Kafka |
| Запустить первый Data Product: `clinic.visit` | Clinic DPO + Data Engineer | Событийный поток из Clinic |
| ClickHouse: первая аналитическая витрина | Data Engineer + BI-аналитик | Дашборд «Визиты по клиникам» |
| Обучение команд (Kafka, DDD, event-driven) | HR + внешний тренер | Базовые компетенции |

**Бизнес-цель:** Сократить время получения управленческих отчётов по клиникам с 24ч (batch ETL) до 1ч (near-real-time).

---

### Этап 2 — Масштабирование (месяцы 7–18)

**Цель:** Перевести все core-домены на событийную архитектуру. Запустить self-service BI.

| Активность | Ответственный | Результат |
|---|---|---|
| Data Product Owners во всех доменах (Lab, Pharmacy, Fintech) | CTO | Доменное владение данными |
| Kafka-интеграции: Lab, Pharmacy, Fintech | Доменные команды | 23 события из каталога (events.md) |
| Flink: потоковая обработка для финтех SLO (<100ms) | Platform Engineer + Fintech | Real-time антифрод, платёжные операции |
| Self-service BI портал (Grafana / Metabase) | BI-аналитики | Самостоятельные отчёты без IT |
| Пилот замены PowerBuilder (одна клиника, React) | Clinic Domain Team | Первый веб-интерфейс клиники |
| Partner API: онбординг первых фарм-партнёров | Integration Team | Каталог препаратов через события |
| DWH: перевод в режим read-only | Migration Team | Новые данные только в доменах |

**Бизнес-цель:** Запуск финтех-продуктов без ожидания ночного ETL. Аналитики строят отчёты самостоятельно.

---

### Этап 3 — Поддержка доменов и экспансия (месяцы 19–36)

**Цель:** Полный Data Mesh. Вывод legacy. Готовность к новым регионам.

| Активность | Ответственный | Результат |
|---|---|---|
| Вывод из эксплуатации DWH SQL Server 2008 | Migration Team | Ликвидация технического долга |
| Вывод Legacy Adapter (Camel ESB) | Integration Team | Полная событийная архитектура |
| Замена PowerBuilder во всех клиниках | Clinic Domain Team | Единый веб-интерфейс |
| Data Mesh governance: Data Contracts между всеми доменами | Arch Committee | Формализованные контракты данных |
| Подготовка multi-region: data residency зоны | Platform Engineer | Архитектура готова к регионам |
| Медицинское оборудование: телеметрия через Partner API | Partner Integration | DeviceTelemetry Data Product |
| AI-диагностика: MVP (MLflow, первая модель) | Отдельная команда | Assess-статус → Trial |

**Бизнес-цель:** Выход в 2–3 новых региона без архитектурных изменений. Полная регуляторная прозрачность.
