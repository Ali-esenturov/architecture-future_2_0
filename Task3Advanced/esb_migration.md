# Куда переезжают обязанности ESB (Apache Camel) — «Будущее 2.0»

> После вывода ESB из эксплуатации его функции **не исчезают** — они распределяются между специализированными компонентами целевой архитектуры.

---

## Сводная таблица

| Обязанность ESB | Кто берёт на себя в целевой архитектуре | Компонент / паттерн |
|---|---|---|
| Маршрутизация | Kafka topics + подписки | Topic-per-domain, consumer groups |
| Трансформации | ACL-адаптеры на границах доменов | Partner Integration, Legacy Adapter |
| ФЛК (форматно-логический контроль) | Schema Registry + доменные агрегаты | Avro + инварианты агрегатов |
| Бизнес-логика | Доменные сервисы | Clinic, Fintech, Pharmacy... |
| Оркестрация | Хореография событий + Saga | Event policies, Flink (stateful) |

---

## Детали по каждой обязанности

### 1. Маршрутизация

**Было в ESB:** центральный маршрутизатор определял, в какую систему пойдёт сообщение (`if type=ORDER → SystemA, else → SystemB`).

**Стало:**  
Kafka-топики **сами являются маршрутом**. Продюсер публикует событие в конкретный топик (`clinic.visit.completed`), а каждый потребитель подписывается только на нужные ему топики. Никакого центрального роутера нет — зависимости инвертированы.

```
ESB: Clinic → ESB [route logic] → Lab / Pharmacy / Analytics

Kafka: Clinic → topic:clinic.visit.completed
             ← Lab (subscribed)
             ← Analytics (subscribed)
             ← Regulatory (subscribed)
```

API Gateway выполняет HTTP-маршрутизацию для синхронных запросов клиентов.

---

### 2. Трансформации

**Было в ESB:** преобразование форматов между системами — XML→JSON, маппинг полей, нормализация кодировок.

**Стало:**

| Сценарий | Компонент | Описание |
|---|---|---|
| Внешние партнёры (MQTT, REST) → внутренний формат | **Partner Integration ACL** | Нормализует телеметрию устройств и фарм-каталоги в Avro-события |
| Legacy ESB/DWH → Kafka (переходный период) | **Legacy Adapter** (Apache Camel, временно) | Транслирует legacy-вызовы в доменные события; выводится к концу Этапа 2 |
| Внутри домена | **Доменный сервис** | Каждый сервис сам преобразует входящие данные в свою модель |
| Аналитические витрины | **dbt** | SQL-трансформации из raw-событий в аналитические модели |

Ключевой принцип: трансформации **децентрализованы** и живут рядом с владельцем данных, а не в центральной шине.

---

### 3. ФЛК (форматно-логический контроль)

**Было в ESB:** валидация форматов сообщений и базовые бизнес-правила на уровне интеграции.

**Стало — два уровня:**

**Уровень 1 — формат (Schema Registry + Avro):**  
Продюсер физически **не может** опубликовать событие с невалидной схемой. Schema Registry отклоняет сообщение до попадания в топик. Backward-compatibility проверяется автоматически в CI/CD.

**Уровень 2 — логика (агрегаты доменных сервисов):**  
Каждый агрегат содержит инварианты — бизнес-правила, которые не могут быть нарушены:
- `Transaction`: сумма > 0, достаточный баланс на счёте
- `Prescription`: срок действия, доза в пределах норм РЛС
- `Appointment`: нет пересечений в расписании врача

ФЛК больше не централизован — он **встроен в домен**, которому принадлежит.

---

### 4. Бизнес-логика

**Было в ESB:** часть бизнес-правил была вшита в маршруты Camel («если статус пациента X — отправить в систему Y»). Остальное — в хранимых процедурах DWH.

**Стало:**  
Бизнес-логика **переезжает в доменные сервисы** — туда, где находятся данные и агрегаты:

| Откуда | Куда | Пример |
|---|---|---|
| ESB-маршруты | Доменный сервис | Логика выбора лаборатории → Lab Service |
| DWH stored procedures | Доменный сервис | Расчёт стоимости услуги → Clinic Service |
| ESB content-based routing | Event policy | «Если DiagnosisSet с кодом Х — автоназначить анализ» → реакция в Lab |

Принцип: **логика живёт рядом с данными**. Ни ESB, ни DWH больше не являются местом для бизнес-правил.

---

### 5. Оркестрация

**Было в ESB:** ESB оркестрировал многошаговые процессы — вызывал системы по очереди, ждал ответов, управлял компенсациями при ошибках.

**Стало — замена паттерна:**

**Хореография (основной паттерн):**  
Каждый домен реагирует на события **автономно**, без центрального дирижёра:
```
VisitCompleted → [policy] → Lab создаёт LabOrder
LabTestOrdered → [policy] → Lab публикует LabOrderCreated
PrescriptionIssued → [policy] → Pharmacy принимает Prescription
PrescriptionFulfilled → [policy] → Fintech инициирует платёж
```

**Saga (для сложных транзакций):**  
Для процессов, требующих компенсации при ошибке (например, платёж за медуслугу):
- Если `PaymentFailed` → `Clinic` откатывает статус визита
- Если `DrugBackOrdered` → `Partner Integration` размещает заказ, `Pharmacy` откладывает отпуск

**Apache Flink (для stateful оркестрации):**  
Для сценариев, требующих агрегации состояния по времени (например, «если в течение 2 часов после VisitCompleted не получен LabResultReady — эскалировать»).

---

## Итог

ESB выполнял роль **единой точки всего** — маршрутизации, трансформаций, валидации, логики и оркестрации. Это и было его главной проблемой: любое изменение затрагивало всех.

В целевой архитектуре каждая обязанность **перераспределена по специализированным компонентам**:
- Kafka берёт маршрутизацию
- ACL-адаптеры берут трансформации
- Schema Registry + агрегаты берут ФЛК
- Доменные сервисы берут бизнес-логику
- Хореография + Saga берут оркестрацию

Результат: нет единой точки отказа, нет центрального узкого места, каждый домен изменяется независимо.
