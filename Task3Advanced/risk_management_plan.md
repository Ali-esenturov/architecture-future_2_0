## Детальный план по категориям

---

### Архитектурные риски

#### AR-1 — Миграция DWH SQL Server 2008
**Меры:** Технические

**Подход: Strangler Fig Pattern**
- Новые бизнес-функции реализуются исключительно в новых доменных сервисах, не в DWH
- DWH переводится в режим чтения для аналитики — запись происходит только через новые сервисы
- CDC (Change Data Capture) используется для синхронизации состояния DWH и новых витрин на переходном этапе
- Данные мигрируют поэтапно, домен за доменом, с двойной верификацией (checksum + бизнес-метрики)
- DWH выводится из эксплуатации только после 90-дневного параллельного запуска нового решения

**Ответственный:** Архитектурный комитет + Data Platform Team  
**Срок:** Этапы 1-3 (постепенно)

---

#### AR-2 — Потеря качества данных
**Меры:** Технические

- Обязательный **data quality pipeline** перед загрузкой данных в аналитические витрины (Great Expectations / dbt tests)
- **Dual-write period**: на переходном этапе данные пишутся и в legacy DWH, и в новые витрины — сравниваются результаты
- Автоматические **data reconciliation отчёты** с алертами при расхождении > 0.1%
- Запрет на деком DWH до прохождения полной верификации всех доменов

**Ответственный:** Data Platform Team  
**Срок:** Этапы 1-2

---

#### AR-3 — Совместимость схем событий
**Меры:** Технические

- Обязательное использование **Schema Registry** (Confluent Schema Registry / Apicurio) с момента запуска Kafka
- Правило совместимости: только **backward compatible** изменения (новые необязательные поля)
- Breaking changes требуют версионирования топика и поддержки старой версии минимум 60 дней
- Автоматическая проверка совместимости в CI/CD pipeline при публикации изменений схем

**Ответственный:** Platform Engineering Team  
**Срок:** Этап 1 (как базовая практика)

---

#### AR-4 — Производительность аналитики
**Меры:** Технические

- Определение **SLO для каждого доменного дашборда** до начала разработки (время обновления, p95 задержка запроса)
- Обязательный **performance benchmarking** на реалистичном объёме данных (10% от production) перед выходом в production
- Использование **ClickHouse** для OLAP-запросов с предагрегацией на уровне Flink
- Индексирование партиций по временным срезам, используемым в типичных отчётах
- Мониторинг consumer lag в Kafka с алертами при превышении пороговых значений

**Ответственный:** Data Platform Team + Domain Teams  
**Срок:** Этап 2

---

#### AR-5 — Безопасность данных
**Меры:** Технические + Управленческие

**Технические:**
- **Zero-trust архитектура**: каждый сервис аутентифицируется через IAM, даже внутри периметра
- Шифрование данных **at rest** (AES-256) и **in transit** (TLS 1.3) для всех хранилищ
- Медицинские данные хранятся **отдельно** от аналитических витрин (физическая изоляция)
- **Audit log** всех операций доступа к чувствительным данным (кто, когда, что читал)
- Регулярный **penetration testing** и проверка конфигурации облака (Cloud Security Posture Management)

**Управленческие:**
- Назначение **Data Protection Officer (DPO)** для медицинских и финансовых данных
- Включение юридической и compliance-команды в архитектурный ревью
- Обучение всех разработчиков принципам secure-by-design

**Ответственный:** Security Team + DPO  
**Срок:** Постоянно, с этапа 1

---

#### AR-6 — Vendor lock-in
**Меры:** Технические

- Использование **cloud-agnostic абстракций**: Kafka (не проприетарные очереди), S3-compatible storage, Kubernetes
- Избегать managed ML-сервисов провайдера — использовать стандарты MLflow, Seldon
- Документировать все зависимости от провайдера в **Architecture Decision Records (ADR)**
- Пересматривать стратегию провайдера при региональной экспансии (учитывать требования data residency)

**Ответственный:** Chief Architect  
**Срок:** Этапы 2-3

---

#### AR-7 — Интеграция новых партнёров
**Меры:** Технические

- Разработка стандартизированного **Partner API** с единым контрактом (OpenAPI 3.0)
- Для каждого нового партнёра — выделенный **антикоррупционный адаптер** вместо прямой интеграции с доменами
- **Sandbox-среда** для тестирования интеграций партнёров без влияния на production
- Self-service onboarding через Partner API Portal с документацией

**Ответственный:** Integration Team  
**Срок:** Этап 2

---

### Организационные риски

#### OR-1 — Сопротивление доменных команд
**Меры:** Управленческие

- Явная поддержка трансформации на уровне **CEO и CTO** — публичный мандат
- Введение понятия **Data Product Owner** в каждом домене: человек, несущий ответственность за качество и доступность доменных данных
- Доменные команды **не теряют контроль** над своими данными — это ключевое отличие от традиционного DWH
- Ранние победы: показать первый рабочий портал самообслуживания в течение 6 месяцев, чтобы бизнес увидел ценность
- Регулярные **демо для бизнеса** с измеримыми результатами

**Ответственный:** CTO + Программный менеджер трансформации  
**Срок:** Этап 1 (критично)

---

#### OR-2 — Нехватка компетенций
**Меры:** Управленческие

- Создание **инженерных гильдий** (Data Engineering Guild, Platform Guild) для обмена знаниями
- Обязательное обучение ключевых инженеров (Kafka, Kubernetes, event-driven patterns) — бюджет на сертификацию
- Найм **2-3 сильных архитекторов** с опытом event-driven трансформаций как ядра компетенции
- Использование **inner source**: успешные паттерны из одного домена публикуются как внутренние библиотеки
- Партнёрство с вендорами (Confluent, Yandex Cloud) для технической поддержки

**Ответственный:** CTO + HR  
**Срок:** Этапы 1-2

---

#### OR-3 — Непрерывность бизнеса
**Меры:** Технические + Управленческие

**Технические:**
- Обязательный **Blue/Green deployment** для всех критических сервисов
- **Canary releases** при переключении трафика с legacy на новые сервисы (начать с 1%, наращивать до 100%)
- Автоматический **rollback** при превышении error rate порога (SLO breach)
- Чётко определённые **RPO и RTO** для каждого домена до начала миграции

**Управленческие:**
- Миграция клинических систем — **только в ночное время и выходные**
- Обязательный **runbook** для каждой миграции с планом отката
- **Freeze-период** перед плановыми миграциями (нет изменений в продуктах)

**Ответственный:** SRE Team + Domain Teams  
**Срок:** Все этапы

---

#### OR-4 — Регуляторные требования
**Меры:** Управленческие

- **Compliance-архитектор** участвует в каждом архитектурном ревью как постоянный участник
- Перед выбором облачного провайдера — аудит соответствия требованиям законодательства
- Для медицинских данных — рассмотреть использование **отечественного облака** или гибридной схемы (on-premise для чувствительных данных)
- Регулярные **compliance reviews** с привлечением внешних аудиторов раз в 6 месяцев
- **Data classification policy**: формальная разметка данных по уровню чувствительности

**Ответственный:** DPO + Legal + Chief Architect  
**Срок:** Этап 1 (до начала облачной миграции)

---

#### OR-5 — Превышение бюджета
**Меры:** Управленческие

- Введение **FinOps практики**: выделенный cloud cost owner, еженедельные отчёты по расходам
- **Stage-gated финансирование**: бюджет выделяется поэтапно по результатам достижения milestones
- Использование **spot-инстанций** для dev/stage окружений; reserved instances для production
- Обязательный учёт **стоимости параллельного запуска** legacy + new в бюджете переходного периода

**Ответственный:** CFO + CTO  
**Срок:** Постоянно

---

#### OR-6 — Размытие ответственности
**Меры:** Управленческие

- Формальные **data contracts** между доменами: схема, SLA, версионирование, ответственный
- **RACI-матрица** для кросс-доменных данных и метрик
- **Архитектурный комитет** как арбитр при конфликтах между доменами

**Ответственный:** Chief Architect + Data Product Owners  
**Срок:** Этап 1

---

### Технологические риски

#### TR-1 — Замена PowerBuilder
**Меры:** Технические + Управленческие

- **Reverse engineering** интерфейсов PowerBuilder с документированием бизнес-логики перед началом разработки
- Привлечение **бизнес-аналитиков клиник** (не IT) для валидации новых интерфейсов
- Постепенная замена: **feature-by-feature**, не переписывание с нуля одним блоком
- Использование современного веб-стека (React/Vue) с пилотом в одной клинике перед массовым внедрением

**Ответственный:** Clinic Domain Team + UX  
**Срок:** Этапы 1-2

---

#### TR-2 — Операционная сложность Kafka
**Меры:** Технические

- Использование **Managed Kafka** (Confluent Cloud / Yandex Managed Kafka) — снимает операционную нагрузку
- Разработка **SRE runbooks** для типовых инцидентов (consumer lag, broker down, rebalancing)
- Мониторинг через **Grafana + Prometheus** с dashboards для каждого топика
- Обязательные **DLQ (Dead Letter Queue)** для всех критических топиков

**Ответственный:** Platform Engineering Team  
**Срок:** Этап 1

---

#### TR-3 — Антикоррупционный слой ESB → Kafka
**Меры:** Технические

- Реализация **идемпотентных продюсеров** в Camel-адаптерах (дедупликация по event ID)
- **Event log**: каждое событие, прошедшее через ACL, логируется с timestamp и source
- **Контрактные тесты** между ACL и Kafka-консьюмерами
- Постепенный перевод: начать с наименее критичных потоков данных

**Ответственный:** Integration Team  
**Срок:** Этапы 1-2

---

#### TR-4 — Региональная экспансия
**Меры:** Технические

- Проектирование архитектуры с учётом **data residency** уже на этапе 1: данные региона хранятся в регионе
- Использование **multi-region облачной конфигурации** с изоляцией данных по namespace/bucket
- Параметризация всех региональных настроек через конфигурацию (без хардкода)

**Ответственный:** Chief Architect  
**Срок:** Этап 3 (закладывать в дизайн с этапа 1)

---

#### TR-5 — Задержки near-real-time для финтех
**Меры:** Технические

- Применение **CQRS (Command Query Responsibility Segregation)**: запись асинхронна, чтение из кеша/материализованного состояния
- **SLO per operation**: для финансовых операций — отдельный fast path с синхронным подтверждением
- Настройка **Kafka producer acks=all** только для критических топиков, relaxed для аналитических
- Нагрузочное тестирование с SLO-ориентированными критериями приёмки перед production

**Ответственный:** Fintech Domain Team + Platform Engineering  
**Срок:** Этап 2
