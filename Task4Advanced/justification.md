# Обоснование событийного подхода — «Будущее 2.0»

> Документ объясняет, почему событийная архитектура на Apache Kafka выбрана в качестве целевой вместо существующей интеграции через ESB (Apache Camel) и монолитного DWH (SQL Server 2008).

---

## Текущее состояние: ограничения Camel ESB + DWH

### Критические ограничения текущей архитектуры

| Проблема | Следствие |
|---|---|
| **Синхронная интеграция через ESB** | Падение одного компонента каскадно останавливает все зависимые сервисы. При сбое ESB — останов всей системы. |
| **DWH как единая точка отказа** | 100% аналитических и оперативных запросов идут в один экземпляр SQL Server 2008. Вертикальное масштабирование упёрлось в лимит железа. |
| **Бизнес-логика в DWH** | Сотни хранимых процедур в DWH делают изменение бизнес-правил дорогим и рискованным. Нет unit-тестов, нет документации. |
| **Пакетная обработка (batch ETL)** | Данные в аналитике устаревают на часы. Финтех-сценарии требуют принятия решений в реальном времени — ETL ночного расписания это не обеспечивает. |
| **Тесная связанность (tight coupling)** | Добавление нового домена или партнёра требует изменений в ESB-маршрутах, затрагивающих другие интеграции. Риск регрессий высок. |
| **Отсутствие истории событий** | ESB не хранит историю сообщений. Аудит операций возможен только через логи, которые ротируются. Регуляторные требования нарушаются. |
| **SQL Server 2008 вышел из поддержки** | Extended Support закончился в 2019. Патчи безопасности не выходят. Медицинские и финансовые данные в уязвимой системе — прямое нарушение регуляторики. |
| **Масштабирование** | DWH не горизонтально масштабируется. При росте клиник или выходе в новые регионы потребуется дорогостоящее железо. |

---

## Целевое состояние: событийная архитектура на Kafka (Преимущества)

### 1. Асинхронное декаплирование → гибкость и отказоустойчивость

**Текущая проблема:** Если ESB перегружен или недоступен, цепочка «Clinic → DWH → Analytics» останавливается полностью.

**Решение с Kafka:**  
Производитель (например, Clinic) публикует событие `VisitCompleted` в топик и продолжает работу независимо от состояния потребителей. Analytics, Laboratory, Regulatory — каждый читает топик в своём темпе.

**Эффект для бизнеса:** Сбой в аналитике не влияет на приём пациентов. Сбой в Pharmacy не блокирует финансовые операции.

---

### 2. Near-real-time аналитика → конкурентное преимущество

**Текущая проблема:** Данные в DWH обновляются ночными ETL-джобами. Бизнес-аналитик видит вчерашние данные. Финтех-решения (одобрение кредита, мониторинг фрода) невозможны в пакетном режиме.

**Решение с Kafka + Flink:**  
Каждое событие (например, `PaymentProcessed`) немедленно попадает в поток. Flink вычисляет агрегаты в реальном времени: сумма транзакций за последние 5 минут, количество отказов. ClickHouse хранит предагрегированные результаты с задержкой секунды.

**Эффект для бизнеса:**
- Врачи видят результаты анализов сразу после публикации `LabResultReady`
- Финтех-антифрод реагирует на подозрительный паттерн за миллисекунды, не на следующий день
- Аналитики строят дашборды на актуальных данных

---

### 3. Горизонтальное масштабирование → готовность к росту

**Текущая проблема:** DWH масштабируется только вертикально (дороже железо). При добавлении новых клиник нагрузка на DWH растёт линейно.

**Решение с Kafka:**  
Kafka горизонтально масштабируется добавлением партиций и брокеров. Потребители масштабируются добавлением инстансов (consumer group). Нагрузка от 5 новых клиник — это добавление партиций в топик `clinic.visit.completed` и несколько дополнительных pod'ов.

**Эффект для бизнеса:** Выход в новые регионы не требует дорогостоящего апгрейда DWH. Пиковая нагрузка (например, конец квартала в финтех) не кладёт систему.

---

### 4. Event Sourcing и аудит → соответствие регуляторике

**Текущая проблема:** ESB не хранит историю сообщений. Для аудита (ФНС, ЦБ РФ, Росздравнадзор) нужно восстанавливать цепочку событий из логов. Это ненадёжно и дорого.

**Решение с Kafka:**  
Kafka по своей природе — append-only log с настраиваемым retention. Каждое событие (`PaymentProcessed`, `LabResultReady`) хранится в топике. Регуляторный отчёт строится не из «текущего состояния», а из неизменяемой истории событий.

**Эффект для бизнеса:**
- Полный аудит-трейл всех финансовых транзакций (требование ЦБ РФ)
- Воспроизведение событий для расследования инцидентов
- Возможность «перемотки» состояния системы для debugging и тестирования

---

### 5. Независимость доменов → скорость разработки

**Текущая проблема:** Добавление нового типа партнёра (производитель медицинского оборудования) требует изменений в ESB-маршрутах, затрагивающих существующие интеграции. Риск регрессий заставляет делать длинные циклы тестирования.

**Решение с Kafka:**  
Новый потребитель подписывается на топик без изменений в производителе. Внедрение нового партнёра — это развёртывание нового ACL-адаптера, который читает `partner.device.telemetry-received`. Clinic Service не знает и не меняется.

**Эффект для бизнеса:**
- Команда Pharmacy может добавить новую фарм-функцию, не координируясь с командой Clinic
- Онбординг нового партнёра занимает недели, не месяцы
- Каждый домен деплоится независимо, без freeze-периодов для других команд

---

### 6. Schema Registry → контрактная безопасность

**Текущая проблема:** Формат сообщений в ESB не зафиксирован. Изменение поля в одном сервисе незаметно ломает потребителей.

**Решение с Kafka + Schema Registry (Avro):**  
Каждый топик имеет зарегистрированную схему. Производитель не может опубликовать событие, не соответствующее схеме. Backward-compatible изменения разрешены; breaking changes требуют версионирования. CI/CD проверяет совместимость схем перед деплоем.

**Эффект для бизнеса:** Ни один рефакторинг Clinic Service не сломает Laboratory или Fintech без явного версионирования контракта.

## Сравнительная таблица: Camel ESB + DWH vs Kafka Events

| Характеристика | Apache Camel ESB + DWH | Apache Kafka + Domain Events |
|---|---|---|
| **Связанность** | Тесная (tight coupling) | Слабая (loose coupling) |
| **Отказоустойчивость** | Каскадные отказы | Изоляция сбоев по доменам |
| **Масштабирование** | Вертикальное (дорого) | Горизонтальное (партиции/pod'ы) |
| **Свежесть данных** | Часы (batch ETL) | Секунды (streaming) |
| **Аудит и история** | Только логи (ротируются) | Постоянный event log (retention) |
| **Добавление нового домена** | Изменение ESB-маршрутов (риск регрессий) | Новый подписчик на топик (без изменений производителя) |
| **Онбординг партнёра** | Правка shared маршрутов | Новый ACL-адаптер (изолировано) |
| **Поддержка SQL Server 2008** | Вышла из поддержки (2019) | Не применимо |
| **Финтех real-time** | Невозможно (batch) | Kafka + Flink: <100ms |
| **Регуляторный аудит** | Трудоёмко, ненадёжно | Нативно через Kafka retention |
| **Контракты API** | Не формализованы | Schema Registry (Avro, версионирование) |
| **Параллельная разработка** | Зависимость через ESB | Независимые топики и сервисы |

## Риски событийного подхода и меры их снижения

| Риск | Мера |
|---|---|
| Операционная сложность Kafka (AR-3, TR-2) | Managed Kafka (Yandex Managed Service), SRE runbooks, DLQ для критических топиков |
| Eventual consistency: данные могут быть «не сразу» согласованы | CQRS для финтех-операций; синхронный fast-path для критических платежей (<100ms SLO) |
| Сложность отладки распределённых потоков | Distributed tracing (Jaeger/Tempo), correlation ID в каждом событии, централизованный event log |
| Дублирование событий (at-least-once delivery) | Идемпотентные потребители (проверка `event_id` при обработке), идемпотентные продюсеры Kafka |
| Схемная несовместимость | Schema Registry с backward compatibility enforcement; автопроверка в CI/CD |

## Заключение

Событийная архитектура на Kafka — не просто технологический выбор, а стратегическое решение, соответствующее целям трансформации «Будущее 2.0»:

1. **Гибкость:** новые домены, партнёры и регионы добавляются без изменения существующего кода
2. **Масштабируемость:** горизонтальный рост вместо дорогого вертикального апгрейда DWH
3. **Скорость реакции:** near-real-time аналитика и финтех-решения вместо ночных ETL-джобов
4. **Регуляторная чистота:** нативный audit trail вместо ненадёжных ESB-логов
5. **Автономность команд:** домены деплоятся независимо, что ускоряет time-to-market

Переход от синхронного ESB к событийной архитектуре — это движение от системы, где **все зависят от всех**, к системе, где **каждый домен независим и отвечает только за свои данные**.
